# Tfke: Split into Web + Backend, and Production Hardening

## Problem Frame

Tfke.id is a "linktree for payment info" — users share their payment details
(bank account numbers, e-wallet handles, phone numbers) via a public link.

Today it is a **frontend-only SPA** with no real backend: all data lives in an
in-memory `mockUsers` object plus `localStorage`, and auth is fake (hardcoded
passwords `password` / `askar123`). Nothing persists across reloads, and any
"secret" payment data would be fully readable.

The goal is to make it **production-ready** by:
1. Splitting into two independently deployable repos — `tfke-web` (static SPA on
   Netlify/Vercel) and `tfke-be` (real API server on the user's VPS).
2. Building the backend that doesn't exist yet: real persistence, real auth, and
   a privacy model where sensitive payment data is **unreadable in a stolen
   database dump or backup**. (Full-server compromise — attacker holds both the DB
   and the env-held key — is explicitly **out of scope** for the permanent tier;
   the ephemeral tier stays zero-knowledge even then.)
3. Replacing the current dark-glassmorphism look with a light, editorial,
   typographic aesthetic modeled on [makingsoftware.com](https://www.makingsoftware.com/).

> Key framing: "split into web + be" presupposes a backend to split out. There
> isn't one. The real work is **build the backend + harden the frontend**; the
> split is a consequence.

## Architecture

```
┌─────────────────────┐         HTTPS / CORS          ┌──────────────────────┐
│   tfke-web (SPA)     │ ────────────────────────────▶│   tfke-be (API)      │
│  React 19 + Vite     │   API base URL via env var    │  Node + Hono + TS    │
│  Netlify / Vercel    │◀──────────────────────────── │  on user's VPS       │
└─────────────────────┘                                └──────────┬───────────┘
        │  WebCrypto                                              │
        │  (encrypt/decrypt                                       ▼
        │   in browser)                                  ┌──────────────────┐
        │                                                │   PostgreSQL     │
        ▼                                                │  ciphertext only │
  key never leaves browser                               │  for sensitive   │
  (ephemeral: in URL #fragment)                          │  fields          │
                                                         └──────────────────┘
```

### Two account tiers (the core model)

| Aspect            | Ephemeral (no login)                        | Permanent (Google login)                       |
|-------------------|---------------------------------------------|------------------------------------------------|
| Create            | No account, instant                         | Requires Google sign-in                        |
| Lifetime          | Auto-deleted 3 days after creation          | Indefinite                                     |
| Editable          | No (create-and-share once)                  | Yes, from any device after login               |
| URL               | Unguessable token, e.g. `/p/:token#k=...`   | `/u/:username`                                 |
| Encryption        | **Zero-knowledge** — key in URL fragment, server never sees it | **Encrypted at rest** — server-held key, decrypts after auth |
| DB breach exposes | Ciphertext only (no key anywhere on server) | Ciphertext only (key in env/secret store)      |
| Server can read?  | No                                          | Yes (after auth / to render public page)       |

## Requirements

**Repo & Deployment**
- R1. Split into two independent git repos: `tfke-web` (existing React SPA) and `tfke-be` (new API server).
- R2. `tfke-web` deploys as a static SPA to Netlify/Vercel; `tfke-be` deploys to the user's VPS.
- R3. `tfke-web` reaches `tfke-be` via a configurable API base URL (env var) — no hardcoded host. CORS on `tfke-be` is restricted to the known web origin(s).

**Backend & Data**
- R4. `tfke-be` is **Node + Hono + TypeScript**, backed by **PostgreSQL**.
- R5. Remove all mock/in-memory data (`mockUsers`) and fake auth; replace with real persistence and a real API.
- R6. API surface covers: create page (ephemeral + permanent), read public page, edit page (permanent only), delete page, and Google auth. The existing `/u/:username` route is repurposed to fetch from `tfke-be` (replacing `PublicProfile`'s `getUser` mock call); the hardcoded `/u/askar` example link and `mockUsers` are removed.

**Auth & Account Tiers**
- R7. Two tiers: Ephemeral (no login) and Permanent (Google/Gmail login). See comparison table above.
- R8. Ephemeral pages are created with no account, reached via an unguessable token link (generated by a CSPRNG, **≥128 bits of entropy**), **auto-deleted 3 days after creation**, and **not editable**. Expiry is enforced **at read time** — a page past 3 days returns 404/410 regardless of whether the cleanup job (R20) has run; the job is defense-in-depth, not the sole mechanism. Read endpoints are rate-limited against enumeration.
- R9. Permanent pages require Google sign-in, are editable from any device, and persist indefinitely.
- R10. No app-managed passwords in v1 — Google OAuth is the only login. The current hardcoded-password flow is removed entirely.
- R21. **Authorization (ownership):** every edit/delete verifies the authenticated user owns the target page (`owner_id` check; 403/404 otherwise). Ephemeral pages have no owner and are not mutable via the authenticated API. _(prevents IDOR — any logged-in user editing another's page)_
- R22. **OAuth flow:** Authorization Code + PKCE with the token exchange on `tfke-be` (client secret never ships in the SPA); explicit redirect-URI allowlist; OAuth `state` for CSRF on the callback; session via HttpOnly + Secure + SameSite cookie (or short-lived token) across the distinct SPA/API origins; CSRF protection on mutating endpoints; logout revokes the session.
- R23. **Permanent username** is chosen by the user at first sign-in, globally unique, with format/length validation and a real-time availability check; not editable in v1; the dashboard is unreachable until a valid unique username is claimed.

**Encryption & Privacy**
- R11. Sensitive payment fields (account numbers, phone numbers, e-wallet handles) are **never stored as plaintext** in PostgreSQL.
- R12. Ephemeral pages use **zero-knowledge** encryption: the browser encrypts before upload; the decryption key lives only in the share-link URL fragment (`#k=...`) and is never transmitted to `tfke-be`. The server stores ciphertext only and cannot decrypt.
- R13. Permanent pages use **encryption at rest**: sensitive fields encrypted with a server-held **env/secret key** (no KMS in v1 — single VPS); `tfke-be` decrypts server-side to render the public page **for any visitor with the link** (public sharing is the feature) and when the owner edits. **Guarantee boundary:** this protects a stolen DB dump/backup that lacks the env key; it does **not** protect against full-server compromise.
- R14. Public profile pages remain shareable by link — the link-holder is the intended audience. The threat model is a **stolen DB dump/backup (without the env key) and transport leakage**. Ephemeral pages additionally resist unauthorized no-link access via an unguessable token; permanent pages live at a guessable `/u/:username` and are intentionally public to any visitor.
- R15. All traffic over HTTPS; all secrets (DB creds, OAuth creds, encryption key) via env/secret store, never committed.
- R24. **Ephemeral link is the secret:** mitigate URL-fragment leak channels — set `Referrer-Policy: no-referrer` on viewer pages, strip `#k=` from the address bar via `history.replaceState` after decode, and warn the creator the link **cannot be recovered or revoked** once shared. Note explicitly that "zero-knowledge" is relative to `tfke-be` only — the key still transits clipboards, browser history, and any messaging app the user pastes the link into.
- R25. **No plaintext in logs:** decrypted payment data (and the encryption key) must never be written to logs, error traces, or monitoring; redact sensitive fields on create/edit/render paths.
- R26. **Key lifecycle:** store a key-version/id alongside each permanent ciphertext to enable rotation; define a rotation procedure; backups must be encrypted (not plaintext dumps) with the key escrowed separately, so a lost key ≠ lost data and a stolen backup ≠ plaintext.

**Frontend Restyle**
- R16. Full visual pivot from the current dark-glassmorphism indigo/violet theme to a **light, editorial, typographic** aesthetic modeled on makingsoftware.com, applied to all pages (Landing, create flow, public profile, dashboard/edit, auth).
- R17. The reference aesthetic is captured via real browser screenshots (the site is behind Vercel bot protection, so a headless/agent browser is needed); design is executed with the `frontend-design` skill and iterated using the `design-iterator` agent with screenshot verification. If capture is blocked, fall back to manual screenshots or proceed from the R27 token spec — the restyle is not blocked on an unverified capture.
- R27. Capture the direction as **concrete tokens** independent of the live reference: named typeface(s) + a specific type scale, a defined light/neutral palette (hex), and a whitespace/measure rhythm. **Explicit anti-slop removal list:** indigo→violet gradients, glass/backdrop-blur cards, blurred glow blobs, gradient-text headlines, and the 3-up icon-in-circle feature grid all go.
- R28. **UX states & flows** for the new paths are designed, not left to implementers:
  - Landing IA presents both creation paths intentionally — a primary "create now, no account" path and a secondary "sign in with Google to keep & edit" — explaining the 3-day-vs-permanent tradeoff at the decision point.
  - Ephemeral create-success screen shows the full link **including the `#k=` fragment** with a prominent copy affordance + confirmation and a "save this now — it can't be recovered, expires in 3 days" warning.
  - Ephemeral viewer states: expired (friendly message + create-your-own CTA), missing/malformed fragment (broken-link, no API call), decryption failure / wrong key (graceful, no crash), and requires-JS-to-decrypt.
  - Create/edit form states: initial, in-progress (encrypting + uploading, submit disabled), success, and error (network / validation / rate-limit).
  - Google sign-in entry is a designed screen replacing the deleted Login/Register forms, including the OAuth redirect/loading state and the first-sign-in username-claim step (R23).

**Production Hardening**
- R18. Environment-based config for both apps (API URL, DB connection, OAuth creds, encryption key, allowed origins).
- R19. Input validation, rate limiting on create/auth endpoints, and secure HTTP headers.
- R20. A scheduled cleanup job hard-deletes expired ephemeral pages (older than 3 days). Mechanism (OS cron vs in-process interval vs pg-scheduled) deferred to planning; correctness does not depend on it (see read-time expiry in R8).
- R29. **TLS termination and certificate renewal** are defined (e.g. nginx/Caddy/Cloudflare); a lapsed cert must not silently downgrade transport. Migration tooling for the Postgres schema is chosen up front — the crypto column layout (ciphertext, IV/nonce, key-version) is a schema decision, not a deferred detail.

## Success Criteria
- Both repos deploy independently — `tfke-web` on Netlify/Vercel, `tfke-be` on the VPS — and the live app works end-to-end against the real backend (no mock data, no fake auth).
- A raw PostgreSQL dump reveals **no readable payment data**: ephemeral rows have no key anywhere on the server; permanent rows are ciphertext without the env-held key. _(This is the explicit guarantee boundary — protection holds for a dump/backup obtained without the env key; it does not hold against full-server compromise for the permanent tier.)_
- An ephemeral page is unreachable after 3 days; a permanent page created on one device is editable after Google login on a different device.
- Every page is unmistakably in the makingsoftware.com visual family, verified by screenshot comparison, with no leftover dark-theme screens.
- Backend hardening verified: OAuth login works with PKCE + CSRF protection; edit/delete reject non-owners (403/404); ephemeral reads are rate-limited and expired pages return 404 at read time; no decrypted payment data appears in logs.

## Scope Boundaries
- No app-managed email/password accounts in v1 — Google OAuth only for permanent pages.
- No ephemeral→permanent "claim/upgrade" flow in v1.
- No payment processing or transactions — Tfke only displays/shares info.
- No team/organization/multi-owner features.
- Ephemeral pages are not editable.

## Key Decisions
- **Own server on a VPS, not BaaS**: user has a VPS and wants control → `tfke-be` is a real, separately deployed API server (not Supabase). _Rationale: control + existing VPS._
- **Two separate repos, not a monorepo**: cleanest independent deploys matching the web/be split. _Rationale: each targets a different host with different tooling._
- **Hono + TypeScript over Express**: modern, lightweight, strong TS DX, keeps one language across web + be. _Rationale: small learning curve coming from React; less boilerplate._
- **Asymmetric encryption model by tier**: ephemeral = zero-knowledge (key in link); permanent = encrypted-at-rest (env/secret key on the VPS, no KMS in v1). _Rationale: throwaway pages get maximal privacy with no recovery burden; editable accounts stay usable across devices, which pure zero-knowledge can't do without a passphrase the user chose to avoid._
- **Permanent-tier guarantee boundary** (decided 2026-05-28): at-rest encryption protects a stolen DB dump/backup only; **full-server compromise is out of scope**. Key lives in env/secret on the VPS — KMS deferred. _Rationale: honest, simple, matches single-VPS reality; ephemeral tier carries the strong zero-knowledge guarantee._
- **Build all of v1 at once** (decided 2026-05-28): both tiers, both encryption models, and the full restyle ship together rather than in phases. _Rationale: user preference; the restyle can still proceed on its own track since it shares no dependency with the backend._
- **Google-only auth for permanent**: avoids app-managed passwords and reset flows in v1. _Rationale: prod-ready auth with minimal surface; email/password can come later._
